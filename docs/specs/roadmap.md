## Hard ordering (violate → rebuild)

- **Build every new webapp data panel on `dashboard.json` polling + the SSE ledger-tail.** That pair is the design, not an interim seam awaiting a cutover; there is no `live-state` endpoint to wait for. **One exemption, and its shape is the rule: a ONE-SHOT TOPOLOGY read may sit beside the poll when the poll is its INVALIDATION signal rather than its transport.** `GET /campaigns/{id}/pipeline` is the only PANEL-feeding one — a pipeline resolution cannot change without a new cycle or a new searchpoint, and `dashboard.json` announces both. A panel whose content changes *while nothing else does* fails that test and rides the poll. `POST /campaigns/{id}/fork-preview` (`manifests.py::preview_fork_steer`) is a read too, but it sits OUTSIDE this rule rather than under it: it is keyed on the operator's pending gesture, which no poll can invalidate because the run does not know about it. Feeding a panel is what puts a read under the rule.
- **BYO per-user API keys — now the load-bearing half, and unbuilt.** Signup is open and each account is metered against `FREE_TIER_SPEND_CAP_USD` + `FREE_TIER_TOKEN_CAP` (lifetime, `quota.py::lifetime_ceilings`), so the host key is bounded — but a user who spends their ceiling has **nowhere to go**. That is the liability now, not the unbounded spend it replaced. Lane A2.
- **HTTP-edge abuse protection is now due.** Cloudflare edge + the per-account ceiling + per-user `JobRegistry` quotas bound the public surface; with the approval queue gone, app-level rate-limiting (C6) is the remaining gap — nothing bounds the NUMBER of accounts, only what each one may spend.

Any new endpoint is multi-tenant by default.

### The optimizer plug point — every optimizer is a manifest

**The contract is [`../architecture.md`](../architecture.md) § Bench and optimizer; the node types and the rules a manifest must pass are [`../developer/node-standard.md`](../developer/node-standard.md) § Optimizer node types.** This section owns the direction: which optimizers, how one is selected and registered, what identity and spend owe it, the members the presets need, and the order the lane closes in.

**The plug point is the whole round, not one call.** A seam at L1's generation call holds scoring, the loop and the individual fixed, and CAPO's population, LEVI's archive and GEPA's Pareto front all live outside it. So a peer is decomposed into members of the node types rather than wrapped as a black box, and whatever it brings — shots, a population, racing, an archive, model routing — becomes a member ours can select too.

| Manifest | Nodes (type) | Its configuration, as node config |
|---|---|---|
| `potter` | `l1_generate`, `l1_critique`, `l2_context`, `l3_plan` (llm) · the δ-adaptive sampler · PoBB (eliminator) · θ election (selector) · `l1_score` (measurement); its escalations are alternative `pipelines:` its controller picks | patiences, `pobb_*`, the `mechanisms` toggles but the bench's degradation fast path, `n_variants`, `prompt_block_catalogue`, `escalation_ladder`, the rebase and terminate capabilities |
| `capo` | `capo_crossover`, `capo_mutate`, `capo_init` (llm) · `few_shot`, `population_rejoin` (algorithm) · `blocks` (sampler) · `paired_t` (eliminator) · `population` (selector) · `score` (measurement) | μ=10, c=4, α=0.2, b=30, z_max=10, k_max=5, γ=0.05 (CAPO App. C.4); the 5M input-token budget is the campaign's (`docs/methods/candidate-elimination.md` § CAPO's population and operators) |

A value that departs from its paper says so beside itself in the manifest.

**Selection is one field and one overlay.** `optimizer: <name>` on the campaign's config picks the manifest and `nodes.{name}.config` adjusts it, exactly as a target pipeline's overlay does — so all five entry points get it with no flag, and two presets run on one box at once, which an install-global choice could not. A named prompt set is a prompt family a node's overlay picks (`promptpotter-self` runs potter's `*_self_optimizing` families).

**Registration is the connectors' and judges' registry, folded.** `connectors/__init__.py::_load/_validate/_add/connector_origins` and its judges twin are one piece of code written twice, so member implementations get no third copy: one stdlib-only helper `(group, builtins, validate) → (table, origins)` serves all three, and a third party ships an optimizer under the `promptpotter.optimizers` entry-point group as a manifest plus its members. A served roster goes into `api-openapi.yaml` before the handler and serves each member's ORIGIN the way `connector_origins()` does — a plugin name greps to nothing in this tree. `IndividualLineage.source` is a free `str`, so `source="capo:capo_crossover"` needs no enum edit. Built-in members live under their preset's directory, a third party's in its own package.

**Off the L4 ban by construction.** [`optimization/CLAUDE.md`](../../promptpotter/application/optimization/CLAUDE.md) § Add no 4th LayerStrategy binds potter's controller. A preset is a sibling manifest with its own `default` pipeline, not a rung beside L1–L3: nothing escalates into another preset, a peer's own reflection runs inside its own nodes the way L4 expresses nesting as re-entrancy, and **no preset runs another's nodes** — a potter critique inside a peer's round would bill our algorithm to the peer.

**The optimizer is OUT of measurement identity in a normal campaign, and IN it for an L4 inner cycle.** `pipeline_resolve.py::_identity_contributions` folds the connector's `identity_config` and the judges, not the optimizer — which is what makes an arm a peer proposes and we already measured replay free, and what makes an N-way head-to-head affordable at all. But in the recursion the optimizer IS the instrument, so `connectors/promptpotter.py::_identity_config` must fold the selected manifest's name and version into the digest or two optimizers' inner cells pool under one key. Same field, opposite answers, decided by which side of the recursion answers — **unstated, this is found by silent pooling**, never by an error. L4 mutates whichever manifest its inner campaign selects, so it tunes any preset.

**Spend: a member's own sends are admitted before they leave.** Peers evaluate internally (GEPA's reflective rollouts, MIPROv2's minibatch trials), and those sends must reach the run's meter or the budget claim is void. The template is `infrastructure/llm/litellm_sends.py::litellm_sends_billed_as`, which admits every litellm send made inside it on the spend book at its bound before it is sent — the way `connectors/harbor.py` bills an agent's sends. `connectors/dspy_module.py` is not the template: it leaves `holds_own_sends` false and reads the student's usage after the call returns, so it bills after the fact and bounds nothing in flight.

**A member is handed frozen `domain/` inputs and never `Cycle`** — the house precedent is a connector getting `InProcessWorkload` and never the session. The moment a member's input carries a store handle or a live client, both the core-is-the-engine boundary and the trusted-code story move — that is the design question to refuse, not to solve. **No new dependency anywhere**: the registry is `importlib.metadata`, and a DSPy-backed member rides the existing `[dspy]` extra, never core ([`ADR-0006`](../adr/0006-embeddable-core-and-extras.md)). `presentation/teleprompter.py` points the other way — it wraps PromptPotter OUTWARD as a DSPy `Teleprompter` for a caller's program, and carries no peer inward.

**Not every peer decomposes cleanly.** Opik's shape is a whole-loop optimizer — `optimize_prompt` with its own metric and `evaluate_prompt` ([`../research/external-constraints.md`](../research/external-constraints.md) § M13; Opik's own [extending-optimizers docs](https://www.comet.com/docs/opik/agent_optimization/)). Reaching it is the outbound direction (a `BaseOptimizer` subclass in `promptpotteropt`), or members that keep its proposals and drop its evaluation. The decomposition is not ours alone ([`../research/external-constraints.md`](../research/external-constraints.md) § L4): [EvoAgentX](https://arxiv.org/abs/2507.03616) plugs AFlow, TextGrad and MIPRO in as swappable evolution algorithms apart from the workflow topology, which is this design seen from the other side. Whether a proposer should itself be an agent stays empirical — [AFlow](https://arxiv.org/abs/2410.10762) beat hand-designed workflows by 5.7% searching them as code graphs, while [AI Scientist v2](https://github.com/SakanaAI/AI-Scientist-v2), the more agentic version, did not reliably beat the templated v1 — so the comparability run is where that gets answered, not argued.

#### The bench score — one evaluator on a held-out set

**The contract is [`../architecture.md`](../architecture.md) § The bench score is not an optimizer's selection, and why selection and estimation need different rows is [`../research/benchmarks.md`](../research/benchmarks.md) § The winner's own number is biased upward.** What this lane builds: the run-init split into search pool, bench set and demo pool, which turns `CampaignConfig.dataset_split` from a display into a partition; the one evaluator scoring each optimizer's final selection — and optionally each round's — on the bench set; and that score as the headline every surface serves and `export.json` reports, so its provenance block states a deployment estimate it can claim. `verify` is the closest existing shape: it re-scores a frozen candidate, C0 included, without touching the cycle. θ election stays potter's selector and stops being anyone's headline. The published BBEH comparison's split already satisfies the requirement.

#### Selector members — parent choice as one acquisition

Scope is WHICH individuals the next round derives from. It is not sample selection (`hard_samples.json`'s acquisition — a different question over a different set); here **acquisition** always means the lineage-tree one.

**Potter runs three selection rules over one tree, and two are one rule with a term missing.**

| Decision | Rule | Code | Member |
|---|---|---|---|
| Which arm survives the round | PoBB — θ posterior against paired priors | `scoring/selection.py::elimination_p_best` | potter's eliminator |
| Which arm the next round derives from | greedy elitism — the round's winner, always | `scoring/selection.py::elect_round_winner` | potter's selector |
| Which ancestor a rebase fork re-expands from | UCB1 over backpropagated θ | `mask/backprop.py::select_rewind_round` | potter's controller |

Rows 2 and 3 answer one question — *given everything measured, where should the next mutation come from?* — with different arithmetic: row 2 is row 3 with the exploration term forced to zero and the candidates restricted to one round's arms. **The direction is one PUCT acquisition, `Q + c · P · √ΣN / (1 + N)`, as potter's selector.** `mask/backprop.py` already carries the tree (`NodeKey = (cycle_id, round)`), per-node visits and value sums, backpropagation and UCB1 against `UCB_EXPLORATION_C`, so Q, N and ΣN exist. The missing term is **P, a prior over this round's fresh proposals**, and L1 is the policy: one field on `L1Variant`, a **predicted lift in θ's units against the parent**. Never a normalized preference — it is dimensionless, cannot be drawn beside θ, means different things in rounds of different widths, and falls out of predicted lifts by normalizing, while the reverse does not hold; a lift's error is predicted minus realized, in logits, which is what the gate below needs. The field generates after `evidence_grounding` and the mutation slots, and three surfaces move with it — the Pydantic model, `l1_generate`'s `answer_format` prose and the regenerated `resolved_schemas`. One number, no justification field (`changes_description` carries the reasoning). A renderer change voids banked origins through `injection_source_digest`; count before expecting the re-measure.

What collapses: greedy promotion becomes the acquisition at `c = 0`, and the rewind stops being a separate mechanism reached only through `fork_proposal`. **`fork_proposal`'s contract does not change** — the layer decides WHETHER, arithmetic decides WHERE, no panel enumerates ancestors (`optimization/CLAUDE.md` § The layer-control channel), and a prior over this round's own arms is not an ancestor enumeration. Not opportunistic for L4: selection must see lineage, not only the round's best ([`../research/external-constraints.md`](../research/external-constraints.md) § Ranked, item 2).

**The rebase forfeit is the acquisition's cost term, and the two land as ONE function** — each rewrites the same expression, so whichever lands second names the other in its diff. UCB1 prices no cost, so a deep ancestor looks free. Measurements are content-addressed, so everything measured replays free at any cut; what a rebase forfeits is (1) **search position**, the θ climbed between the target and the frontier; (2) **evidence leverage**, visits above the cut stop informing the new branch; (3) **future cache misses**, predictable from observed reuse at comparable cuts (`LineageNode.cached_samples`). Against all three sits the gain of a target whose adjacent child edges differ by ONE data-affecting knob (`application/knobs.py::classify_config_diff`): a controlled one-parameter contrast. Shape: a pure fold beside `divergence.py` and `scenario.py` over the `SpineCycle` list UCB already loads, emitting a per-cut `ForfeitReading`, **served first** on the tree's course nodes, then folded in as `Q − λ·forfeit` with λ beside `UCB_EXPLORATION_C`. It never reaches L2 as prose.

**No learned value model.** A surrogate predicting fitness from prompt text would need an error smaller than the lifts the loop chases, which already need paired comparison and Holm to resolve. Measure that before proposing it — fit one on the banked archive, hold out candidates, compare its error to the observed lift distribution; a negative result closes the axis. Until then Q stays **measured θ, never estimated**.

**Gated on one reading, built first:** bank the predicted lift as an **inert field** — written, served, read by nothing that decides — and compare it against realized θ lift. An LLM's stated expectation about its own proposals may be uninformative or anti-correlated, and this is measurable before any acquisition is built. The reading and the operator display are the same artifact, so they ship together.

**Five states the acquisition can enter and cannot report**, each served with it or it is unfalsifiable:

- **Visit concentration** — `accumulate_node_stats` computes visits for every node and `select_rewind_round` keeps one argmax, so a tree that never branched reads exactly like one whose branches all lost.
- **What the leader leads on** — serve the value and exploration terms, never their sum alone: winning on curiosity is not winning on evidence.
- **Prior entropy across the round's arms** — mode collapse and near-duplicate candidates as a number.
- **Calibration trend across rounds** — whether the proposer is improving, degrading or was never informative; no single round answers it.
- **Ruler provenance on a backpropagated Q — a correctness finding, not a display gap.** `NodeStats.value_sum` adds θ read on a ruler that grows (`domain/ruler.py`'s `unmeasured_delta` caveat), so a deep node's `q` mixes scales. Establish on the overlap line whether the drift is material before the acquisition consumes `q`.

**Where they live.** The three node readings ride `candidates/ForestCard` through `candidates/Forest`'s `CladogramCtx`, sourced from `/tree` — no second cladogram. Prior entropy rides `candidates/FitnessRankSummary` from `dashboard.json`. The calibration trend is the one new element: a per-round series about the PROPOSER, which hung on a candidate chart would read as a candidate's number, fed by `dashboard.json::rounds[]`. Every reading is served ([`../developer/adding-a-surface.md`](../developer/adding-a-surface.md) § 3), one source per data class. `<entry-point-parity>` must be decided, not defaulted: the trend reaches `evidence` too, or browser-only is declared in [`../../promptpotter/presentation/CLAUDE.md`](../../promptpotter/presentation/CLAUDE.md).

**The prediction's display is a forward view — no toggle, no new element.** `DashboardCandidate.label` is composed at mint, so every arm has a row before it is measured, and for an unmeasured arm the prediction is the row's only content. One mark, drawn always, read by arm state: minted → the prediction alone; measuring → the prediction over a growing bar; selected → prediction and bar, the gap being the error; **cut by the eliminator → the prediction marked RESOLVED-WITHOUT-MEASUREMENT**, the state that will be got wrong, since a pending mark left in place reads as loading forever — the failure `DashboardCandidate.invalid` exists to prevent. Predict in θ and accept that it resolves at selection rather than continuously: predicting in composite fitness would reopen the accuracy-vs-θ confusion `candidates/AbilityInfo.tsx` closes. No band by default — a prediction has no sampling error, and a whisker drawn like a measured one claims it was measured.

**Open.** What stands in for θ on unmeasured children, and whether the normalization window is the forest or the round (`select_rewind_round` min-max normalizes across the forest, and a degenerate forest collapses to pure exploration). Whether an arm the eliminator cut is a legal parent — a policy question, not a derivation. Three names to settle when it lands: `selection` names both survival and expansion; `prior` is taken by PoBB's paired comparison, so the predicted lift is not called one; `NodeStats.value_sum` sums θ, so it is `theta_sum`, and a round is a measurement, not a simulation.

  where the calibration round's own rows hold it; lifting it needs a check-in step that measures,
  a banked-matrix record, and a sampler input that is not a round document.
- **SIFT's members** (§ SIFT reproduction). The **self-proposer** — the parent agent run on its own source and evaluation logs, returning one patch; a proposing node is handed its parents, which is the whole of the self-reference. The **archive-wide parent selector** with SIFT's `P(i) ∝ exp(−α·r_BT − β·r_acc − η·log(1+v))`; their "an unevaluated node inherits its parent's accuracy" lives inside this function and nowhere else — it may steer a choice, never become a measurement. The **candidate-level pairwise judge + regularized Bradley-Terry**, new because `promptpotter/judges/` grades cells, not candidates: two candidates' full source in, a preference out, bounded comparisons per new node, ranks out to the selector and the eliminator. The **`fixed_gate` eliminator** — their small pass/fail block as a literal replacement for PoBB, a priority queue by `r_BT + r_acc`, the full search split on the chosen node.

6. **The budget dimension** (PAID, strictly after 5): the same arms at two or three budget points, so cost is an axis rather than a constant. ### SIFT reproduction — their method as a PromptPotter preset

**SIFT-exact is a preset, and the paper is the ablation ladder from it.** [SIFT](../research/landscape.md#sift--self-improvement-via-fast-tree-search-paper) (the Darwin Gödel Machine line, with a judge-ranked evaluation front end) is reproduced as the `sift` manifest, its parts as members (§ Members the presets need). The reading is then one potter member swapped in per arm through the node overlay — PoBB for the fixed gate, Rasch θ rank for accuracy rank, the hard-first sampler for the fixed subset, the held-out adoption gate — each paired against SIFT-exact at one budget and one seed set, so every claim reads "X instead of theirs buys Y at equal cost". The self-referential half (the improved optimizer proposes the next round) is [`l4-outer-loop.md`](l4-outer-loop.md) § Open, self-adopt mode.

**Its manifest runs nothing of potter's:** a sampler frozen to one subset and one order, the `fixed_gate` eliminator, no controller, one variant per round, `max_rounds` at their step count, the search pool at their search-subset size and the full benchmark as the bench set.

**One part is not a member — code-artifact candidates, the design-bearing gap.** SIFT patches the agent's source and tools; a candidate here is prompt fields and pipeline params. The new candidate is a file set or patch, content-hashed into measurement identity, loaded per episode by an agent runner (Harbor or something lighter — S3 below decides) — an extension of § Evolving agent harnesses.

Optional and later: expansion overlapping measurement ("disaggregated") — needed only to match wall clock, and it waits on § Run admission + concurrent serving.

**Models: cheap and already measured, not theirs.** S1 and S2 run on the dataset's own declared model; S3's agent is `qwen/qwen3.7-flash`; the candidate judge is `openai/gpt-oss-120b` throughout — the Harbor agent and the `sealqa` judge in [`../operations/dataset-reasoning-matrix.md`](../operations/dataset-reasoning-matrix.md). Whether to rerun on SIFT's own models is decided when the paper is written, not before.

**Benchmark.** Polyglot is not wired here; check Harbor's registry for an adapter before building the code-artifact dataset.

**Declared inexact.** No code release: the judge prompt, the BT pseudo-count, the gate threshold and the queue's tie-breaks come from the paper or are chosen and stated. Their CPU-hours column is not reproducible — § Captured, CPU-hours.

**Proposed sequence — a suggestion, not a commitment. Risk goes last.** Every rung waits on the plug point's neutral migration (§ The optimizer plug point, stage 2); code artifacts touch measurement identity and need a new Harbor agent, so nothing waits on them.

- **S1 — SIFT's search on a surface we already have (the transition milestone).** The candidate judge, then the parent selector and `fixed_gate` — no code artifacts. ### Probe rounds — what they mean, and why the lever is not wired

**This section stays at full length — it is a written SPEC, not stale description of an unwired lever.** It reads as prose about nothing because `L2ContextOutput` carries no `action` field, so a doc-shrink pass scores it as dead. Operator-decided: don't compress it, don't fold it into a code pointer, and don't file the missing field as drift.

**A probe round spends its whole budget interrogating ONE thing** — one axis, one variable, one recurring mistake — instead of spreading a broad mutation set across the failure surface. The distinguishing move is **more candidates on a narrower question**, so the round returns a real answer about that one thing rather than one noisy sample of it.

**L2 cannot request one today: there is no `action` field on `L2ContextOutput`, deliberately.** The shipped version selected samples by *warning* while the prompt asked L2 which *axis* to probe, and the warning inventory behind it was later deleted — leaving a set that only fills on backend degradation. On a healthy run it is empty, so the round scored every candidate 0/0 and persisted `accuracy: 0.0`, indistinguishable downstream from a genuinely terrible candidate, while still paying its optimizer calls and consuming a round. `l2_targets_l1_surface` even counted the choice as conformant — L2 scored 100% precisely by picking the action that measured nothing.

The lever was removed rather than guarded, because a guard leaves a no-op action sitting on L2's menu. **Re-running warned queries is degradation triage, not a search action**; conflating the two is what put an empty-set path in the candidate scorer. Build the real thing as defined above: pick the target from measurement (a peaked axis, a recurring failure cluster), widen `n_variants` for that round only, and select samples by *relevance to the hypothesis* — never by a set that is empty whenever the run is healthy.

With a campaign selected, the panel also shows what it runs, read from the same served resolution one level up. It is one element; where you click decides the level.

### Agent-tool parity — PromptPotter as a callable tool inside an operating agent

Two halves of one question, and they are siblings: parity widens how PromptPotter is **invoked**, § Application radius widens what it **emits**.

Today PromptPotter is driven by a human or by Claude via `/potter-run`. The next invocation surface is **parity as a first-class agent-callable tool**: an *operating agent* — the user's own, an agent harness like dsh, or an ML-research agent like NVIDIA's AutoResearch or verl — calls PromptPotter as one move in its toolbox. Those callers stack rather than compete: a harness is where an operator sits, verl and NeMo RL only start above the weights line, and a gateway sits below both. Parity means the MCP tool exposes the CLI/skill lifecycle — mint, run, supervise, read results — so an agent can operate a campaign end-to-end. Mechanism already on the board: **C5**.

**Deliberately held, not just unscheduled.** The REST API is the integration surface for now — protocol-agnostic, and callable by anything that can hold a browser session, which is the live constraint rather than a detail — **the inbound-credential gap is owned by [`../developer/stable-api.md`](../developer/stable-api.md) § 8. What is NOT stable**. MCP would need the same credential and would add a protocol on top of the gap. The protocol's shape is settled — [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28) with the Tasks extension, where a long-running call returns a task handle (`tasks/get` / `tasks/update` / `tasks/cancel`) rather than a polling or webhook scheme of our own ([`../research/external-constraints.md`](../research/external-constraints.md) § TOOL) — so the hold is the credential gap alone. Revisit once that closes and a concrete caller asks.

### Application radius — what PromptPotter EMITS, and the standing DSPy rule

**The standing rule governs every future integration, not just this one: whenever we plan an ecosystem expansion — a new integration, export, registry, tracing sink, or callable surface — DSPy is the reference we read before designing.** Not because their code is better; a source study says plainly that it is not. **Their ecosystem beats ours while their code does not**, and that asymmetry is the lesson: reach is won by being consumable, not by being well-built.

**M13 reverses the arrow without retiring the rule.** Being consumable stays the goal, but it now runs both ways: we install into DSPy as an optimizer, *and* DSPy's optimizers run inside us as manifests (§ The optimizer plug point). The second direction is the one that makes reach a *measurement* claim rather than a distribution one — a peer that runs here is a peer we can price. **Opik is the next host for the first direction, later rather than now:** its Agent Optimizer already sells six algorithms behind one API, GEPA among them, so PromptPotter registered there is one call away for a buyer who already pays for autonomous optimization ([`../research/landscape.md`](../research/landscape.md) § Langfuse and Opik).

**The gap, located.** PromptPotter today is *terminal* — it ends at "here is your prompt", and a human carries that to production. DSPy is *ambient*: it is already what runs, and optimization is one operation performed against it. The gap is not features but that our output is a **report** where theirs is an **artifact a running system consumes**.

**The boundary is not negotiable: we write a file and provide a reader. We never load, host, route, or hot-swap.** The swap belongs to the host — a registry alias, a path the app reads at boot, a committed artifact. Becoming a serving framework is permanently out of scope.

**The artifact** is `cycles/{id}/export.json`; its reader contract and the four rules it obeys are owned by [`../developer/stable-api.md`](../developer/stable-api.md) § 5c. Two of those rules invert findings in DSPy's source: `Signature.dump_state` writes fields positionally and `load_state` zips them back with `strict=False`, so a signature that gained a field reloads a scrambled prompt with no error at all — hence **field names, never positions**; and their artifact carries no provenance, which is the half we compute and they do not.

**The radius stops at the model the winner was won on.** [Why Prompt Optimization Works, and Why It Sometimes Doesn't](https://arxiv.org/abs/2605.26655) found optimizer edits that help one benchmark often fail on another across four model families, and [Prompting Inversion](https://arxiv.org/abs/2510.22251) reports a scaffold that helps GPT-4o and hurts GPT-5. So an export names its model, and a model swap is a new run, never a copy of the winner; the pitch leads with mid-tier and open-weight serving models, where gains do not shrink or invert the way they do on the strongest reasoning models.

**Open — two of the three consumers.** Our own runtime is built. `to_dspy` lives in the `promptpotteropt` repo, never here (the dependency arrow is one-way — [`ADR-0006`](../adr/0006-embeddable-core-and-extras.md)), waits on Phase C, and applies the winner to a *live* program rather than emitting DSPy state, sidestepping the positional-zip corruption. MLflow is unwritten and targets the **Prompt Registry** (`register_prompt` / `load_prompt` / `search_prompts`), **not a model flavor**, because we produce prompts, not programs. Its registry semantics (placeholders, versions, aliases) bind the write-back: [`../research/external-constraints.md`](../research/external-constraints.md) § TOOL.

### Judged and turn-structured scoring

**Tracked as C2b, and most of it has SHIPPED.** The judges, the grading call path (reuse cache, 429 retry, heartbeat, metering, all decided once at `judges/call.py::ask`), plural judges keyed by the term the formula reads, and the `retrieve → ground → answer` step schema are all live; `promptpotter/judges/CLAUDE.md` owns every contract and reason behind them. It deliberately does NOT live in `pipeline.yaml::nodes` — `node_config_items` is the walk a bulk model steer follows, and that is exactly the boundary a judge may not sit behind.

It unblocks datasets no matcher can grade, and the first is wired and running: `datasets/sealqa-longseal-12/`. Two more record being stuck on it — `email-tagging`'s free-text CRM fields and `screen-taste-v0`'s rating.

**The conversation reaches a formula, and only as scalars.** `domain/scoring.py::turn_scalars` projects `n_turns`, `n_tool_calls` and `{step}_turns` at measure time, beside the `{step}_{reward}` terms the harbor connector banks. The raw `turns` list stays unreachable from a formula on purpose and must remain so: the compiler's AST allowlist has no subscript, no attribute access and no `len`, and `turns` is the first key `compact-archive` moves out of a cold row, so a formula that walked it would raise on every cell it had already scored. Two routes reach scoring from a conversation and there is no third — this projection, or a judge that reads the turns and banks a term.

**What remains, at three distances.** *Per-step difficulty* is the larger prize and the only part needing a run rather than a decision; its blockers and its one non-skippable precondition — bank each step's term separately, which the shipped schema now does — are at [`../methods/verdict-resolution.md`](../methods/verdict-resolution.md) § Phase 3. The two authored rubrics have since been screened on the `def880` campaign and BOTH were removed: they saturated and graded a property of the cell rather than of the arm, so they could not separate arms however many paid for them (`datasets/sealqa-longseal-12/campaign.yaml::judges` records the numbers). The criterion that screen established — **does the term vary across arms on the same cell** — is what any future rubric owes before a campaign funds it. *Scoring* one step is already config and step-agnostic. *Optimizing* one step is near: the candidate prompt is trial-scoped (one `SKILL.md` per episode), so an arm mutates the whole episode however narrowly it is scored, and the open design is whether a declared step becomes a NODE — one per step with its own `prompt_info` and `param_keys` — which makes the existing `campaign_config.exclude_nodes` the step selector and adds no new channel. It costs generalizing `connectors/harbor.py`'s singular `AGENT_NODE`. Separately: not RUNNING the later steps, where the cost saving lives, since Harbor runs every declared step and `_unscoreable_step` raises on a truncated one.

**PARTIAL PIPELINE GENERATION — far, and deliberately so.** Today L1 always proposes a COMPLETE pipeline. The feature is that it may propose a partial one, with *which* subset being **L2's** decision — the first place the escalation layer chooses a search SHAPE rather than a search direction.

- **Do not open it until a real pipeline is blocked without it.** With few steps a whole-pipeline proposal is both cheaper to reason about and strictly more expressive. The gain appears only where a pipeline has many steps and no way to tell which one moved the number.
- **Its trigger is a FORK, not a stall.** The signal is L2 reaching a two-way split it cannot choose between: two strategies, no evidence favouring either, and a whole-pipeline arm that would confound them. A plain stall belongs to the existing escalation ladder.
- **It is a human-in-the-loop design cycle, not an implementation ticket.** What a partial proposal may touch, how a partial arm compares against a whole one, and what a δ ruler does with arms of different shapes are all open and none is answerable from code.

**SHIPPED, and the residual it asked for is measured.** A grading that failed past its retry left `rescore_results` raising inside `measure_sample`, and the catch-all banked the cell as an ERROR — discarding a backend answer already paid for, and tripping `query_loop.py::_abort_reason` on `PIPELINE` so the candidate's whole remaining walk went with it. The residual, asked for here before acting: **zero banked cells**, because no dataset's formula names a judge term yet — recount with `compact-archive inventory` before quoting a denominator. `formula/rescore.py` now resolves such a row to UNSCORED — measurement kept, both verdict keys absent, out of every denominator — and a formula that RAISES still halts loud, since that one is a contract bug every cell fails.

### Evolving agent harnesses
**Tracked as C7, ahead of v1, and the connector half has SHIPPED** — `connectors/harbor.py` plus `datasets/harbor-tbench-regex-log/`. The artifact to evolve becomes an **agent harness** — an agent's prompts, tools and control flow — rather than only a single LLM call or a declared pipeline. Wording alone is the smaller lever on agentic tasks: LangChain's deepagents went from 52.8% to 66.5% on Terminal-Bench 2.0 with the *same* model through prompt, tool and middleware changes ([harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)).

**Do not re-open "whose harness — dsh or LangChain".** That question binds the design to one vendor's harness and inherits its mutation surface. [Harbor](https://github.com/harbor-framework/harbor) sits a layer below — evaluation infrastructure, in `pytest`'s category — and drives ~30 agents behind one `BaseAgent` interface, so which harness is under test is one line in a dataset's `harbor_tasks.yaml` rather than a design commitment.

Two things in the remaining gap are real rather than cosmetic, and both shipped: a **labelless cell** (`Sample.ground_truth is None`, since a verifier grades where no label exists) and an **arm-time observation-key contract** (`Connector.required_observation_keys`). The **per-cell wall clock** L4 solved privately is now `Connector.cell_envelope_s`, enforced for every backend at the one seam a cell is measured. The per-cell **spend** bound is built too: a harbor cell reserves what one episode bills as declared (`connectors/harbor.py::_sent_spend_bound`), and every send the agent makes is admitted at its own bound (`infrastructure/llm/litellm_sends.py`). What stays open is harbor's **per-cell wall clock** — it declares no `cell_envelope_s` yet, so only Harbor's own `task.toml` bounds an episode's time. A cap on measured counts is not a substitute: tokens and dollars jitter run to run, so it would cut the same cell on one run and not the next.

SkillOpt, DarwinX and AutoDesign already evolve harnesses for a frozen model, and DarwinX states our own one-armed-search argument back at us. What that comparison leaves standing is what a PromptPotter version must keep rather than re-derive — sequential elimination, cost-per-fitness, subset-invariant ability. Their benchmarks are agent environments `harbor` can now measure but PoBB's cost model still cannot bound, so adopting the target does **not** mean adopting their evaluation suite.

**Under M13 they stop being only a comparison and become candidate ARMS.** The WikiSkill / SkillOpt *setting* is already here as Harbor's advanced-vs-primitive skill delivery, so what the plug point adds is their *method* beside ours on the same cells — which is what answers "are their methods actually better at the same model", a question the published numbers cannot settle because nobody held the model constant. The factorial follows for free: optimizer × delivery mode, read by `evidence --grid`.

**The target worth building toward is a skilled agent.** That means one agent equipped with many skills, where each skill is maintained, evaluated and updated separately, rather than one monolithic prompt tuned as a whole. The design is ours to build: it is one configuration of our agent toolkit, and we optimize each skill as well as evaluate it. [NVIDIA SkillEvaluator](https://github.com/NVIDIA/skillevaluator) covers only the evaluation half of that one design, and it is not a competitor ([`../research/landscape.md`](../research/landscape.md) § NVIDIA SkillEvaluator). Adopting and testing it is for later. Its three tiers — **validation** (is it safe and well-formed?), **deduplication** (does it repeat guidance?) and **live evaluation** (does it help the agent, measured against not having it?) — are a search *strategy*, so the part our infrastructure already carries enters as **L2 and L3 context**, not as new machinery. Measured lift is the only admission ticket: [SkillsBench](https://arxiv.org/abs/2602.12670) found curated skills gain +16.2 pp on average yet hurt 16 of 84 tasks, and self-generated skills gain **zero** — so an LLM's rewrite alone never admits a skill, and SkillsBench is the external harness to report skill results on. Whether the optimizer should itself become a skilled agent rather than the fixed L1–L3 loop is the same kind of question, and an empirical one: [AFlow](https://arxiv.org/abs/2410.10762) beat hand-designed workflows by 5.7%, [AI Scientist v2](https://github.com/SakanaAI/AI-Scientist-v2) did not reliably beat its templated v1, and [EvoAgentX](https://arxiv.org/abs/2507.03616) keeps the search algorithm apart from the workflow shape so both can be tried on the same cells.

**Now, on what exists.** The tiers live in the shared optimizer prompts (`assets/optimizers/potter/pipeline.yaml`): when the candidate is an agent skill, `l2_context/1` checks the tiers in order and names the first failing one in `axis_targeted`, and `l3_plan/1` replans onto it; every other target reads those prompts unchanged. The one unbuilt piece is tier 1's size rule, which is code.
- **Tier 2 → no repeated guidance.** A skill grows by appending, and appended guidance overlaps what the skill already says until two lines disagree. So the prompts say: prefer merging or deleting a line over adding one, and never restate guidance the skill already carries. `mutation_memory` already shows L1 what was tried, so the repeat is visible to it. SkillsBench found focused skills of 2–3 modules beat comprehensive documents, and [Trace2Skill](https://arxiv.org/abs/2603.25158) is the proposer pattern to prefer over a free rewrite: it patches from success and failure traces and merges them into one conflict-free skill.
- **Tier 3 → the ablation move, and a no-skill anchor.** The prompts say a line that cannot beat its own absence is removed rather than reworded, which makes deletion a first-class mutation. The baseline is measurable today: an origin with an empty `SKILL.md` is an ordinary campaign, and the matched-parent lift on the same cells prices every later skill against it. What does not exist is the no-skill arm running *beside* the search inside one cycle; that waits on M13's arms.
- **Tier 1 → a strict validator, the one piece that is code.** The candidate is the skill's body; `connectors/harbor.py::_write_skill` owns the frontmatter, so a mutation cannot break the header. What a mutation *can* break is the [Agent Skills spec](https://agentskills.io/specification)'s size bound, a body under 500 lines ([`../research/external-constraints.md`](../research/external-constraints.md) § ranked 5). A `validators/l1_strict.py` rule would reject an oversized body before it runs, at $0; it is unbuilt, so today only the L2 prompt names the bound. Security review and dependency checks stay with SkillEvaluator, but tier 1 also holds a security floor no mutated body may cross — no Unicode Tag characters, no instruction to read secrets or environment variables, no outbound calls or exec/eval — the attacks [SkillSpector](https://github.com/nvidia/skillspector) (71 patterns; a risk score above 50 means do not install) and [Cisco skill-scanner](https://github.com/cisco-ai-defense/skill-scanner) already scan for, and a SkillSpector-class scan before a candidate is measured is the long-run form. The skilled agent moves `description` into the search, and the frontmatter rules then join this check.

**Before the library grows — skill routing.** Selection degrades as the library grows (measured at 52, 102 and 202 skills, up to 21% worse, with no safe threshold given), from wrong-skill picks rather than from context ([More Skills, Worse Agents?](https://arxiv.org/abs/2605.24050); [`../research/external-constraints.md`](../research/external-constraints.md) § SKILL). The skilled agent needs its routing design before its library reaches a few dozen skills, not after, and overlapping descriptions are what seed the wrong picks, so mutual distinguishability against sibling skills becomes an objective; [SkillRouter](https://arxiv.org/abs/2603.22455) shows retrieval at library scale is embedding-based and also reads skill bodies. Prose skills themselves are the open question: in [SkillWeaver](https://arxiv.org/abs/2504.07079) skills written as callable APIs transferred from a strong agent to a weak one (+54% on WebArena), and ours are prose.

**Later, on SkillEvaluator.** Semantic overlap measured against the whole skill library rather than asked for in the framing, its four-bucket synthetic datasets, and Skill Lift as a served statistic beside ours.

The unit of optimization then becomes the skill and the unit of acceptance becomes the library. Evolving one skill is re-measured against the others it ships with, which is where tier 2 and tier 3 meet.

### Anonymous preview tier
Spec only — **do not build it before the chat backend exists** (`presentation/api/routers/chat.py` is absent), because an anonymous meter with no conversation to meter is a writer with no reader.

- **Its own issuer sentinel, and `is_anonymous` asked BEFORE the operator arm.** This is the trap, not a detail: `quota.py::spends_the_hosts_own_key` reads a missing issuer as "came through the terminal, which only the operator reaches", so an anonymous identity built by leaving the issuer unset resolves as the box operator and is metered by nothing. The sentinel makes the two distinguishable; the ordering makes the distinction bind.
- **Empty capability set.** No command verb, no launch, no ingest, no dataset write — it converses and reads, and every action surface is a sign-in prompt. Nothing is added to `CAMPAIGN_CAP_BY_NAME`, so `_require_capability_for` refuses each verb with no per-verb exception to keep in step.
- **One shared tenant.** `UserStore.get_or_create` writes a `user.json` per tenant, so a tenant per visitor is an unbounded directory-creation surface reachable without authentication. One tenant gives the spend a reader for free: a single row in `jobs/install_spend.py::read_install_spend`.
- **A global daily pool is the ceiling; the per-visitor allowance is UX.** A per-visitor cap is defeated by discarding the visitor, so the only figure that binds is one install-wide daily pool. `admit_launch`'s reservation does not apply — an anonymous turn is one call, and anonymous cannot launch a campaign at all.
- **No trustworthy origin signal ⇒ refuse the request**, or the pool becomes a scrape budget assembled from millions of small turns.

### Operator-steered fork
Two rules survive the build. `config_overrides` carries the fork's whole `OptimizationConfig` delta — run limits **plus** the policy toggles — so **a fork at offset 0 A/Bs a behaviour knob in isolation** without moving the global default; that is the standing "behaviour-knob change → sibling cycle" workflow. And `max_rounds` on a fork is an absolute target, not a remainder: the fork's counter continues from its parent.

**Teardown-only design was rejected — do not re-propose** (it reverses the folder-UI §0 commitment). The two state surfaces it concerns are owned by [`../operations/persistence-and-state.md`](../operations/persistence-and-state.md).

### Run admission + concurrent serving
Nothing is open in the mechanism. Campaigns run concurrently up to a resolved capacity, a full box QUEUES rather than refuses, and the queue drains least-served-first; every entry point takes the same slot from the same line, the terminal included. The substrate is an OS file lock, so admission is atomic across processes and a dead producer's slot returns at once — which is also C6's predecessor: `--workers > 1` and a containerised worker need no second mechanism. Owned by [`../operations/access-model.md`](../operations/access-model.md) § What bounds resource use.

- **Open — full-speed-each needs more provider quota, not a better divider.** Two busy users on one key each get roughly half the throughput however the window is shared; only **Lane A2** buys more. It is cheap once reached: an `api_key` dimension on `get_llm_client`'s cache key gives every tenant its own limiter.
- **Distinct axis — sample look-ahead *within* one run.** `capacity` is how many CAMPAIGNS the box admits; look-ahead is how many CALLS one scoring round holds in flight, so it does not cross-bill and is gated separately on `campaign.lookahead`. **Open:** the ceiling is a hand-set constant per connector rather than measured peak-RSS headroom (there is an OOM post-mortem in `runner/inner/spawn.py`), and inner and outer still share the process-global `RateLimiter` with no per-tenant slice. Only TermNorm's is measured, and only on `llm_only` — its web-search pipeline meters one Brave query per cell against a per-key rate limit, unprobed at that depth; `harbor`, `dspy` and the recursion keep guesses. Re-test: `seed-screen --parallel N` at rising N on a dataset of that backend, reading wall clock and error rows per depth. **Open, forward:** the horizon is a worst case — a cell is launched only if no rule can POSSIBLY cut before it — so early in a walk PoBB's reachable-but-unlikely cut holds look-ahead near `n_min`. A horizon priced in expected waste (P(cut before i) × a call) would launch deeper at a bounded expected cost. Boundary: [`../operations/access-model.md`](../operations/access-model.md) § host-admin ↔ user.

### Lineage mask
The read side is [`../operations/mask-projection.md`](../operations/mask-projection.md); code SoT `application/mask/`. The **write side — fork-from-divergence — shipped**: `fork-cycle` carries `keep_rounds`, which swaps the offshoot trigger for `OPERATOR_REWIND` so rounds `0..N-1` are lifted, and `ConfigOverrides.scoring` carries the criterion into the fork's effective config. The alternative branch still materialises only as a real, measured fork the operator chose to run — never a stored forecast tail — which is why persisted mask identity is still not a thing: the criterion rides the seed the fork already writes.

Open as **Lane C8**: the SAMPLE-SET half, and it is a different substrate rather than a second knob. A scoring mask forks on the existing rails because it re-selects a *candidate* from arms the run measured; a mask that changes which samples a round buys needs a replayable measurement ORDER seeded into the fork, which `CycleSeed` does not carry and `ForkSpec` does not root at. Until it does, a sample-subset mask previews and stops there.
